# M4: воспроизведение управленческого решения

Сохранённая рекомендация берётся из `config/m3_decision.json` и пересчитывается через принятый M3. `config/management.json` содержит предложения участников, правил оплаты, доступа, KPI, рисков, переноса и этапов. `config/assumptions.json` содержит явно неизвестные условия и предложенный горизонт. Исходные CSV, коэффициенты, веса и M3-вход не изменяются.

Из корня проекта:

```powershell
.venv/Scripts/python.exe -X utf8 -B scripts/build_management.py
.venv/Scripts/python.exe -X utf8 -B scripts/build_management.py --output-dir reports/evidence/m4_reproduction
```

Команды заново рассчитывают один и тот же release. Полный комплект сначала записывается в уникальную `.staging-<uuid>` внутри `results/m4_releases/`, созданную обычным `Path.mkdir()` с наследованием доступа родителя. Существующие права и владельцы каталогов не меняются. Затем проверяются сохранённый JSON, CSV, три Markdown, их размеры/хеши и повторный рендер из сохранённого JSON. Завершённая папка получает уникальное имя в `results/m4_releases/<release_id>-<generation>/`. До активации все пять окончательных путей перечитываются и проверяются тем же механизмом, что использует reader; временный pointer также проверяется после записи. Единственная точка активации — атомарная замена `results/m4_current.json`. При обычной ошибке записи/завершения/активации старый pointer и прежние файлы сохраняются; неудачная первая сборка не создаёт текущий выпуск. Код возврата ненулевой. Завершённые папки автоматически не удаляются: читатель ранее открытого выпуска продолжает пользоваться его файлами. Cleanup касается только собственных временных объектов; при отказе доступа права не меняются, первичная ошибка сохраняется. Незавершённые staging-папки не используются потребителями. Гарантия относится к обычным I/O-ошибкам, а не физическому отказу носителя.

Чтобы проверить текущий комплект и получить пять абсолютных путей:

```powershell
.venv/Scripts/python.exe -X utf8 -B scripts/build_management.py --current
.venv/Scripts/python.exe -X utf8 -B scripts/build_management.py --current --output-dir reports/evidence/m4_reproduction
```

В каждой завершённой папке: `results/m4_management.json`, `results/m4_finance.csv`, `docs/management-note-draft.md`, `docs/stress-summary-draft.md`, `docs/presentation-draft.md`. Старые плоские results больше не являются output; старые docs заменены указателями на эту инструкцию. Программный потребитель вызывает `backend.app.management_release.read_current_release(destination)` **один раз на комплект** и использует возвращённые `(manifest, artifacts)`; функция проверяет все хеши и согласованность и не подставляет исторические файлы при ошибке. Не перечитывайте pointer отдельно для каждого файла. `--output-dir` создаёт отдельное дерево для сравнения; пять payload-файлов побайтно воспроизводимы, generation-путь при повторе новый. Для запуска из другой cwd укажите абсолютные пути Python/скрипта/output. Сеть/LLM/внешние API не нужны.

В приложении откройте «Реализация». После реального пересчёта видны сохранённый состав, таблицы, адресные обязательства, карточки услуг, альтернативы, STRESS и календарь. Кнопка загружает тот же состав в ручной конструктор. Изменённый ручной состав или новые веса не наследуют старую договорную схему. Кнопки JSON/CSV/Markdown сохраняют именно показанный bundle. Поле `finance_csv` вычисляет Python при построении того же bundle: CSV-кнопка не делает второго запроса и не пересчитывает деньги во frontend. Если локальная конфигурация изменилась A→B, до обновления экрана все скачивания принадлежат A; после пересчёта — B. Пока пересчёт идёт или завершился ошибкой, старые карточки/скачивания скрыты. Поздний ответ отменённого запроса игнорируется.

`GET /api/implementation` отдаёт актуальный расчёт, Python-generated `finance_csv` и три редактируемых материала. `GET /api/implementation/finance.csv` отдельно пересчитывает текущую конфигурацию для прямых API-клиентов; этот endpoint не используется кнопкой показанного набора. Для сохранения согласованного UI-комплекта используется `finance_csv` из JSON-ответа. Сервер не отдаёт произвольные файлы проекта. При повреждении источника, несовместимом M3, неполной карточке, отсутствующей ссылке или неверных долях C0 — явная ошибка; прежние документы не используются как fallback. Для больших локальных управленческих конфигураций введён отдельный предел 262144 байта, HTTP-ввод остаётся ограничен прежними 65536 байтами.

Каждый денежный поток содержит `basis`, сумму, единицу, плательщика, получателя, срок и условие. Адресный gap считается в Python как `max(OPEX_i-CASH_i,0)`; он не добавляется в canonical CASH/KCASH/OPEX/C0. В CSV `TOTAL` содержит портфельный gap и сумму lot gaps, индивидуальные строки — собственный gap. `stress_action` помечен совпадающим с основной стратегией в JSON/UI, поэтому строки этой роли не надо суммировать как отдельный портфель.

Release identity включает хеши management, assumptions, сохранённого M3-входа, источников и fingerprint канонического результата. Денежные таблицы материалов берутся из того же bundle; текст описывает только эту сохранённую версию. Исторические M0-карты кандидатов в `service-design.md`, реестр `sources.md` и принятая аргументация `m3-choice.md` сохранены для происхождения. Текущие полные материалы находятся только в папке, проверяемой `--current`.

Версия render/release-контракта входит в identity и меняется при изменении генерируемых материалов; схема pointer остаётся отдельным контрактом. Локальные ссылки Markdown рассчитаны на расположение текущего выпуска в дереве проекта: методология и реестр находятся в корневом `docs/`, источники — в `case_source/`, ссылка презентации на записку — внутри того же поколения. Отдельное дерево `--output-dir` или Markdown, скачанный в произвольную папку, ещё не является автономным комплектом с этими зависимостями; переносимый комплект собирается и проверяется в M5/M7.

Для M5 содержание записки разбито на десять основных разделов и детальные карточки/протоколы внутри них. При вёрстке подробные карточки и протоколы можно вынести в приложения со ссылками из основного текста, сохранив обязательные выводы и суммы в основном объёме. Сценарий презентации имеет двенадцать слайдов с отдельными заметками докладчика. PDF-объём и читаемость в M4 не проверяются и не заявлены готовыми.

Схема assumptions закрыта: обязательны schema_version, stage, status, team_name (строка либо null), selected_portfolio и assumptions. Записи A01–A15 требуют id, topic, value и status; topic/status — непустые строки, value — непустая строка, строгое целое либо null (неизвестно). Необязательные reason/resolve_by/source/limitation/unit/label/proposal_ref — непустые строки, fields — непустой список непустых строк; их можно опустить, explicit null запрещён. Неизвестные поля везде отклоняются, включая amount_expression. Конфигурационные ошибки дают обоим endpoints 503 management_unavailable; source errors сохраняют отдельный код. CLI не публикует ничего до успешной валидации. Ошибки программирования renderer не маскируются как ошибка конфигурации.


## Уточнение ORG

Существующие карточки AGRI C / ENV A / FLOOD A / TRANS C уточняют продукт→действие→пользу, условную классификацию доступа, выбор зрелого измеримого сервиса либо пилота неизвестного местного применения, вклады/обратную связь и ограниченный порядок при внезапной потере доступа. Полные условия и 10 плановых KPI — в management/protocols, краткие выводы — в основных 12 страницах и 12 слайдах; стресс остаётся отдельной страницей. Реальные спрос, договоры, SLA, ресурсы и достигнутые KPI не заявляются.

M4 render-контракт /4 различает новое содержание и сохраняет точный рендер прежних /2 и /3 поколений. Сборщики создают новые identity без изменения исходного решения, чисел, весов, рангов и source/result fingerprints. O1–O5: предоставленные PDF с точными физическими страницами, DOI и SHA-256 в sources. Полные статьи частные, не обязательная зависимость runtime или публичной поставки. Внешние ссылки и библиография заново не проверялись.
