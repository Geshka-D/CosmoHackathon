# Контракт модели и выбора — M1/M2 и реализация M3

Статус: расчёт M1 и ручной M2 приняты; реализация поиска/MCDA/sensitivity M3 передаётся независимым Tester/Evaluator. Активный выбор — `config/m3_decision.json`, полные результаты — `results/m3_decision.json`. Источники — [sources.md](sources.md); исходные M0-приоритеты сохранены в `config/decision.json`, неизвестные/допущения — `config/assumptions.json`. Финансовые договорённости M4 и финальные документы ещё не завершены.

## Решение и применимость

Инструмент предназначен для условного межрегионального заказчика: сравнить состав из четырёх сервисов и режимы доступа, проверить общие ограничения и объяснить, кто использует и оплачивает результат. Детерминированная модель подходит для сравнения синтетических вариантов на единых условиях. Она не оценивает рыночную стоимость реальных проектов и не доказывает операционную готовность. Высокий score не заменяет подтверждения плательщиков, качества и прав на данные.

В M0 ни одна четвёрка не рекомендована. Предлагаемая архитектура: неизменные источники → строгий loader/валидация → adapter исходного S4 → метрики и ограничения → сравнение/MCDA → ResultBundle → UI/JSON/CSV/документы. Frontend не получает отдельную копию экономических формул.

## Исходные поля и период

| Поля S5 / результата | Единицы и способ использования |
|---|---|
| `c0_mrub` | млн руб., единовременное создание; отдельное финансирование запуска |
| `opex_mrub_per_year`, `anchor_cash_mrub_per_year`, `commercial_cash_mrub_per_year`, `cash_mrub_per_year` | млн руб./год; год эксплуатации при исходных параметрах |
| `vpub_mrub_per_year` | млн руб./год по синтетической шкале общественной ценности, не денежный доход |
| `t_rep` | исходный безразмерный индекс, смысл не установлен, не срок окупаемости |
| `readiness_1_5`, `resilience_1_5`, `scale_1_5` | индексы 1–5, методики не раскрыты; простые средние |
| `federal`, `public_core` | настоящий boolean; строки `false` нельзя превращать через `bool('false')` |
| `territorial_archetype`, `capability_groups`, `lot_id`, `mode_id` | исходные категории/идентификаторы; без вымышленных регионов/правовых названий |

Источник не задаёт календарный старт и многолетний горизонт. Используется интерпретация «C0 при запуске + год эксплуатации». План на 12 месяцев — собственная дорожная карта, не пропорциональный пересчёт годовой экономики пилота. Нельзя рассчитать NPV, окупаемость или ликвидность из этих данных без новой явной модели.

## Каноническая арифметика S4

Для каждой пары лот i — режим m:

```text
C0_i = source.c0_mrub * m.k_c0
OPEX_i = source.opex_mrub_per_year * m.k_opex
VPUB_i = source.vpub_mrub_per_year * m.k_vpub
ANCHOR_i = source.anchor_cash_mrub_per_year * m.k_anchor
COMMERCIAL_i = source.commercial_cash_mrub_per_year * m.k_commercial
CASH_i = ANCHOR_i + COMMERCIAL_i
Портфельные C0/OPEX/VPUB/CASH = суммы соответствующих строк
KCASH = сумма CASH_i / сумма OPEX_i
t_rep/readiness/resilience/scale = простое среднее по выбранным строкам
```

Компоненты ANCHOR/COMMERCIAL раскрываются адаптером по исходной формуле CASH, не заменяют S4. KCASH не среднее коэффициентов отдельных лотов, не прибыльность. VPUB не складывается с CASH; сумма VPUB разрешена только как каноническая синтетическая агрегация, а реальные KPI общих событий разных сервисов не суммируются без устранения двойного счёта.

## Девять обязательных условий

| Код | Условие | Допуск |
|---|---|---|
| `exact_lot_count` | ровно 4 уникальных лота; обёртка M1 требует ровно 4 строки для полного результата | точное равенство |
| `territorial_archetypes` | >=3 среди `federal=false` | целое |
| `capability_groups` | >=2 нормализованных групп | целое |
| `public_core_lots` | >=2, для A/B/C только A даёт true | целое |
| `c0_limit` | C0 <=1300 BASE, <=1180 STRESS | предел +1e-9 |
| `opex_limit` | OPEX <=360 млн руб./год | предел +1e-9 |
| `vpub_floor` | VPUB >=1000 по шкале кейса/год | предел -1e-9 |
| `kcash_floor` | KCASH >=0.6 | предел -1e-9 |
| `t_rep_floor` | средний t_rep >=0.63 | предел -1e-9 |

SSA исключён только из территориального счётчика, остальные его вклады сохраняются. PNT/InSAR, PNT, InSAR объединяются в `PNT/InSAR`; EO, SATCOM, SSA отдельны. Это правило учёта, не взаимозаменяемость технологий. У неизменного портфеля BASE→STRESS сохраняет все метрики; `c0_headroom = limit-C0` меняется из-за лимита. Перенос этапов оплаты не уменьшает полный канонический C0.

Ошибки формата/ID/дубликатов/нечисловых и non-finite входов — отдельная ошибка до ядра. Экономически недопустимый, корректно заданный набор — успешный расчёт с нарушениями. Обёртка M1 закрывает дефект S4: пять строк с четырьмя уникальными лотами отклоняются до расчёта. Исходник не изменён. Пустой/неполный набор получает INCOMPLETE; все девять диагностик NOT_EVALUATED, `ok=null`. Для непустого частичного набора доступны промежуточные факты, у пустого численная экономика `null`.

Фактический ResultBundle M1 описан в [api.md](api.md). Решения полного набора берутся из `core.check_constraints` с eps=1e-9, не из округлённых подписей. `margin` положителен в допустимую сторону, `deficit=max(-margin,0)` сохраняет сырой выход за границу; `tolerance_accepted=true` отмечает отклонение, принятое ядром по eps. Строки сортируются по lot_id/mode_id до суммирования; исходный порядок сохранён отдельно. CASH остаётся канонической суммой; раскрытие ANCHOR/COMMERCIAL её не заменяет и не прибавляет VPUB.

## Предварительно объявленный метод MCDA (реализация M3)

Полный перебор A/B/C: C(8,4)×3^4 = 5670 вариантов. Сначала девять обязательных условий выбранного сценария, затем ранжирование допустимых. Значения 1031/143/888 независимо подтверждены в M0; production-поиск и рейтинг в M1 не реализованы и не используют эти числа как входы.

Веса Architect: VPUB .30, C0 .15, OPEX .10, KCASH .10, t_rep .05, readiness .10, resilience .15, scale .05. Основной приоритет — общественная полезность; финансовая исполнимость и устойчивость далее. Это предпочтения команды, не перевод рубрики жюри 75/25. До ранжирования также объявлен равновесный профиль .125 по каждому показателю.

R — все допустимые BASE-портфели этой версии/хешей. Шкала сохраняется при STRESS и сравнении карточек. Для выгод `z=(x-min_R)/(max_R-min_R)`; C0/OPEX минимизируются, `z=(max_R-x)/(max_R-min_R)`. При `max=min` вклад 0 для всех, правило выводится пользователю. `score=sum(w*z)` без предварительного округления. Ties: меньший C0, затем лексикографический ID из отсортированных пар lot_id/mode_id. Нормализация и population_id в M0 ещё не вычислены, значения null.

Редактируемые веса конечны, неотрицательны, сумма положительна; при перенормировании показываются исходные и применённые. Риск двойного акцента OPEX/KCASH и корреляций раскрыт; интервальная полезность индексов не доказана. Неизвестное обязательное условие реализуемости не исчезает от нулевого веса.

Sensitivity: два разных заранее объявленных веса VPUB/C0, каждый отдельно ×0.8 и ×1.2. При множителе a веса j: `den=1+(a-1)*w_j`, `w'_j=a*w_j/den`, остальные `w'_i=w_i/den`. Заново score/ранги; вывести лидера, место исходного решения, смену состава/режимов/запасов. В M0 не запускалось. Это анализ предпочтений, не официальный стресс и не вероятностный прогноз. D выключен; Парето и совместная сетка — OPTIONAL.

## Адресное финансирование (собственная диагностическая надстройка)

```text
net_operating_balance = CASH - OPEX
portfolio_funding_gap = max(OPEX - CASH, 0)
lot_funding_gap_i = max(OPEX_i - CASH_i, 0)
addressed_funding_need = сумма lot_funding_gap_i
```

Значения выводятся отдельно от канонических метрик; дополнительное покрытие не увеличивает CASH/KCASH. Политика M0 — нет межлотовых трансфертов. Положительный итог портфеля не финансирует дефицит другого договора автоматически. По каждой будущей выбранной строке: полный C0 отдельным источником; anchor один раз; commercial без гарантии спроса; адресный gap отдельным обязательством плательщика. Суммы только из будущего ResultBundle, сроки и получатели — `config/management.json`. Неизвестные авансы и сезонность остаются условием ликвидности, кредит не выручка.

## Контракт будущего ResultBundle и доказательства

Версия схемы и кейса; хеши источников; канонически сериализованный проверенный вход и fingerprint; состав/режимы; поля/коэффициенты/формулы каждой строки; агрегаты; все девять проверок BASE/STRESS с limit/fact/headroom/violation; единицы и период; веса/направления/границы R/population_id; assumptions; альтернативы и управленческая конфигурация. Imported результаты недоверенные: пересчитать сервером по входам. Финальные документы — снимок одной сохранённой release-конфигурации, без подстановки объяснения другого портфеля.

Исторический M0 audit — ограниченный smoke Coder; независимые M0 результаты записаны в M0_REPORT.md. Реализация M1 имеет отдельный Coder smoke и ожидает новых Tester/Evaluator. Сверка финальных документов и чистый комплект относятся к M5–M7. Противоречия формул/порогов S1–S5 при чтении не выявлены; неопределённости горизонта/индексов/юридических названий записаны явно и не исправляются догадками.

## Отображение в M2

В UI C0 — затраты запуска; OPEX/CASH — годовые величины; VPUB — отдельная синтетическая общественная ценность; KCASH — каноническое отношение сумм; t_rep — заданный безразмерный индекс. Формулы и скорректированные вклады каждой пары с исходной строкой/коэффициентом доступны из ResultBundle. Исходные CSV/официальные пороги readonly. Режим A имеет public_core=true, что само по себе не означает бесплатность всего сервиса или заключённый договор.

Сравнение ручных вариантов не выбирает финальный портфель. Разницы считаются Python относительно первого сохранённого варианта и не превращаются в сводную оценку. BASE/STRESS используют одну экономику состава и разные C0 caps. 0–3 лота остаются INCOMPLETE/NOT_EVALUATED, null отображается как «—». JSON сохраняет только настройки, источники и IDs; импортированные настройки проходят валидацию и серверный пересчёт. Поиск/MCDA добавлены отдельным M3-путём ниже; финансы M4 и финальные документы остаются следующими этапами.
# Реализация M3 и действующий выбор

MCDA, полный поиск и sensitivity реализованы в `decision_model.py`, `search.py`, `sensitivity.py`, `decision.py`. Текущий выбор воспроизводит `config/m3_decision.json`; полные шкалы, роли альтернатив, сырые/применённые веса, baseline и результаты находятся в `results/m3_decision.json`. Исходный `config/decision.json` остаётся неизменным M0-предпочтением, не готовым ответом. Обоснование фактического компромисса — [m3-choice.md](m3-choice.md).

Числа ниже, помеченные M0/M1, описывают историческое основание; актуальный поиск получает свои счётчики из CSV и official core, не из контрольных таблиц. Все BASE-feasible образуют одну R вне зависимости от весов; постоянный показатель даёт 0 без перераспределения веса. Строгое сравнение score не использует EPS из ограничений. Сначала неокруглённый score descending, затем C0 ascending, затем lex sorted lot/mode. Для максимум-VPUB/minimum-C0 предметной стратегии: собственная цель, меньший C0, lex состав.

Шкала индексов трактуется как интервальная полезность только в модели команды; равенство интервалов не установлено источником. C0/OPEX могут коррелировать, OPEX входит в KCASH, t_rep/readiness могут описывать связанные свойства. Совместный вес C0/OPEX/KCASH в M0 больше веса одного VPUB: это не лексикографическая первичность общественной ценности и не распределение официальных 75/25 баллов. Равные веса и четыре perturbations показывают последствия предпочтений, а не вероятность или устойчивость ко всем внешним событиям.

Основной выбор: лидер BASE по текущему сохранённому профилю (M0 по умолчанию). При STRESS сначала проверить тот же состав и режимы без изменения экономики. Если допустим, сохранить; иначе первый STRESS-feasible по тем же весам, шкале и ties. Действие принимает условный заказчик с плательщиками/владельцами задач до необратимых обязательств (A10); прошлый C0 не возвращается, переходные затраты неизвестны. Условия качества, прав и финансирования ещё относятся к M4.
